# Fix log — 2026-09-03

## Date folders kept the organize-run timestamp

- **Symptom:** Newly created date folders appeared in Explorer with the current run's **Date modified** value instead of the newest routed file's timestamp.
- **Root cause:** The executor refreshed folder mtimes before optional empty-directory cleanup, which could touch those parent folders again; it also attempted refreshes for moves that failed.
- **Change:** Refresh only successful moves and validated no-op files, after directory cleanup, and log when the filesystem declines a refresh.
- **Regression risk:** A failed move no longer influences a date folder's timestamp; existing folders with correctly routed files still receive metadata-only refreshes.

## Default rules produced vague folders

- **Symptom:** Recognizable project documents, source files, and unknown files landed in broad `Documents`, `Code`, and `Misc` folders.
- **Root cause:** The built-in rules had only a few topic heuristics and used broad extension buckets as the normal fallback.
- **Change:** Added narrow topic rules, document-purpose and source-language destinations, an ArangoDB project route, and an explicit `Needs Review` queue for ambiguous names.
- **Regression risk:** Files with overlapping topic words follow the higher-priority specific rule; the smoke check covers representative project, coursework, code, and unknown-file routes.

## CI smoke rules used obsolete destinations

- **Symptom:** The CI smoke script reported failures after the date-first routing change, even though the rule engine generated the intended destinations.
- **Root cause:** `tools/smoke_rules.py` still expected the pre-date-first folder layout and exited successfully despite failed expectations.
- **Change:** Updated expectations to the current date-first layout, corrected vacation-name matching for underscore-delimited filenames, and made failed expectations return a non-zero exit code.
- **Regression risk:** The smoke script now correctly blocks CI when routing changes break its documented contract.

## macOS smoke path construction was not portable

- **Symptom:** The macOS runner failed before expectation checks with a `Path.relative_to` error.
- **Root cause:** The synthetic root used a hardcoded Windows path (`C:/...`), which `pathlib` treated as a relative component on macOS.
- **Change:** The smoke script now creates its root with `tempfile.mkdtemp()` and `pathlib.Path`, so every runner uses a native absolute path.
- **Regression risk:** Temporary smoke roots are left to the operating system's temporary-directory cleanup policy.

## Temporary path aliases broke relative-path reporting

- **Symptom:** Windows and macOS CI failed in `Path.relative_to` even with a temporary root.
- **Root cause:** The OS exposed equivalent temporary paths under different aliases (Windows short names and macOS `/private` symlink resolution).
- **Change:** Resolve both the temporary root and each generated destination before calculating relative paths.
- **Regression risk:** None; this affects only smoke-report formatting, not file operations.

## Release builds prompted for Flutter installation

- **Symptom:** Fresh Windows, macOS, and Linux runners failed when Flet asked for interactive Flutter SDK installation; Windows also hit a CP1252 encoding error rendering the prompt.
- **Root cause:** Release jobs ran `flet build` without supplying stdin or disabling Rich terminal output.
- **Change:** Release workflow now disables Rich output and pipes an affirmative response to Flet's bootstrap prompt on every platform.
- **Regression risk:** The workflow automatically accepts Flet's required SDK installation, which is intentional for ephemeral CI runners.
