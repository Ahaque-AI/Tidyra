# Tooling rules

## 1. `uv` only — no `pip`, no `requirements.txt`, no manual `venv`

Tidyra's Python interpreter, virtualenv, dependency manager, and script runner are all `uv`. Reasons:

- One tool, one lockfile (`uv.lock`).
- The CI uses the same toolchain.
- Onboarding is `git clone && uv sync` — no "now install Python".

Never add `requirements.txt`, never document `pip install -r ...`, never run `python -m venv`. If you need a new dependency, `uv add <package>`.

## 2. `pyproject.toml` is the project config

- `[project]` — name, version, dependencies, optional-dependencies, scripts, urls.
- `[build-system]` — `hatchling` only; do not change the build backend without an ADR.
- `[tool.ruff]` + `[tool.ruff.lint]` + `[tool.ruff.format]` — lint and format rules.
- `[tool.mypy]` — strict mode.

If you add a runtime dep, also update `[project.optional-dependencies]` if it is dev-only.

## 3. mypy is strict

`pyproject.toml` declares `strict = true` plus `warn_unused_ignores`, `warn_return_any`, `disallow_untyped_defs`. Domain code (`src/tidyra/domain/`) MUST stay 100% type-clean. Adding a `# type: ignore` requires an inline comment explaining why — and ideally a follow-up issue.

## 4. ruff lint and format must pass

`uv run ruff check .` and `uv run ruff format --check .` are the CI gate. New code should follow the existing rules — do not silence a lint with a `# noqa` unless you can justify it in the PR description.

## 5. Resource packaging

Anything in `src/tidyra/resources/` that needs to ship with the wheel must be listed under `[tool.hatch.build.targets.wheel].artifacts`. Today:

```toml
artifacts = ["src/tidyra/resources/*.toml", "src/tidyra/resources/*.svg"]
```

If you add a new resource type (e.g. `.json`, `.css`), extend the glob — or, if the asset is large, switch to `[tool.hatch.build.targets.wheel.force-include]`.

## 6. Load packaged resources via `importlib.resources`

Do not hard-code paths under `src/tidyra/resources/...` from code. Use `from importlib.resources import files; files("tidyra.resources").joinpath("name.ext")`. The pattern is documented in [presentation/brand.py](../../../frontend/brand.py).

## 7. Windows path discipline

- Use `pathlib.Path` — never `os.path.join`.
- Do not assume forward slashes. `Path("a/b")` is portable.
- Flet desktop APIs that expect paths accept `Path` or `str`; pass `str(Path(...))` if the API chokes on `Path`.
- Test the Windows shell with PowerShell syntax; do not embed `bash` snippets in user-facing docs. The README and CONTRIBUTING use PowerShell examples.

## 8. No global Python

Do not call `python` directly for project commands. `uv run python ...` is the only sanctioned way to invoke a one-off Python snippet during development. CI runs `uv run python ...` too.

## 9. Lockfile commits travel with dep changes

`uv.lock` is committed. Every change to `pyproject.toml` dependencies must include the matching `uv.lock` change in the same commit. A dep-only change without a lockfile change is a CI red flag.

## 10. Cross-platform packaging — `flet build` + GitHub Actions

Tidyra ships as a Windows `.exe`, macOS `.app`, and Linux AppImage. The
builds are produced by **`flet build`** on a per-platform runner. Source
stays in git; the binaries are attached to GitHub Releases (NOT
committed to the repo).

### Icon assets

The brand mark is generated by `tools/build_icon.py` into `assets/icons/`:

| File | Purpose |
|---|---|
| `assets/icons/tidyra-icon.ico` | Windows build icon (consumed by `flet build windows`) |
| `assets/icons/icon.png` | Linux build icon (consumed by `flet build linux`) |
| `assets/icons/png/tidyra-icon-{16,32,48,64,128,256,512,1024}.png` | Multi-size PNG set. The macOS runner assembles them into an `.iconset` and runs `iconutil -c icns` to make `tidyra.icns`. |
| `src/tidyra/resources/tidyra-icon.ico` | Packaged with the wheel, read at runtime by `presentation.brand.icon_path()` for `page.window.icon`. Generated as a side-effect of the same build script. |

Regenerate any time the SVG changes: `uv run python tools/build_icon.py`.

### Local build commands

The first build on a fresh machine downloads Flutter SDK (≈ 500 MB).
Subsequent builds reuse the cache.

The entry point is configured in `pyproject.toml`'s `[tool.flet.app]`
block (`path = "src/tidyra"`, `module = "main"`), so the build finds the
entry shim at `src/tidyra/main.py` automatically. The shim re-exports
the async `main` from `tidyra.presentation.app` so the whole `tidyra`
package is bundled and imports resolve at runtime.

Windows:

```powershell
uv run flet build windows `
  --project tidyra `
  --product Tidyra `
  --org dev.abdulhaque `
  --bundle-id dev.abdulhaque.tidyra `
  --copyright "MIT License"
```

Output: `dist/windows/tidyra.exe` plus the supporting runtime DLLs. Zip
`dist/windows/` to ship.

Linux:

```bash
uv run flet build linux \
  --project tidyra \
  --product Tidyra \
  --org dev.abdulhaque \
  --bundle-id dev.abdulhaque.tidyra \
  --copyright "MIT License"
```

Output: `dist/*.AppImage`.

macOS (must run on a Mac — `iconutil` is macOS-only):

```bash
uv run flet build macos \
  --project tidyra \
  --product Tidyra \
  --org dev.abdulhaque \
  --bundle-id dev.abdulhaque.tidyra \
  --copyright "MIT License"
```

Output: `dist/macos/tidyra.app`. The CI workflow zips it with `ditto`.

If `flet build` ever reports "main.py not found in the root of Flet
app directory", check that the `[tool.flet.app]` block in
`pyproject.toml` is intact. The expected shape is:

```toml
[tool.flet.app]
path = "src/tidyra"
module = "main"
```

`path` is the directory `flet build` packages; `module` is the entry
filename inside that directory (no extension). `flet build` looks for
`<path>/<module>.py`. With our src layout, the package root is
`src/tidyra/` and the entry shim is `src/tidyra/main.py`.

If `flet build` fails with `socket.gaierror: [Errno 11001] getaddrinfo
failed` while downloading the build template (the URL is
`https://github.com/flet-dev/flet/releases/download/v<version>/flet-build-template.zip`),
the host can't reach GitHub right now. Run
`uv run python tools/prefetch_flet_template.py` once the network is
back — it downloads the template into
`~/.flet/cache/build-template/v<version>/flet-build-template.zip`
where `flet build` looks first. The CI release workflow runs this step
defensively on every matrix job so transient DNS issues don't fail
the build.

### CI builds

Two GitHub Actions workflows:

- `.github/workflows/ci.yml` — runs on every push to `main` and every PR. Ruff + mypy + smoke test across the three OSes and Python 3.11/3.12/3.13. No builds, no artifacts.
- `.github/workflows/release.yml` — runs on every `v*.*.*` tag push and via `workflow_dispatch`. Builds Windows/macOS/Linux artifacts in parallel, then aggregates them into a GitHub Release with the matching CHANGELOG section as the body.

Code signing is **not** wired up. Unsigned Windows builds trigger a
SmartScreen warning; unsigned macOS builds trigger a Gatekeeper
warning. We accept those warnings for the alpha phase — see ADR-0009.

### What goes in git, what does not

- **In git**: the Python source, the docs, the rules, the SVG brand source, the **generated** icon set under `assets/icons/`, the build script, the workflows.
- **Not in git**: `.exe`, `.app`, `.AppImage`, `.dmg`, `.icns`. These attach to GitHub Releases via the release workflow. The `.gitignore` excludes `dist/` so accidental local builds do not pollute the tree.
